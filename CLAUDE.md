# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Code Style
Use clean layered architecture where possible. 

## Project

Doorbust is a Go eCommerce backend targeting oversell-free, idempotent inventory guarantees under high contention (flash-sale / "doorbuster" style load). `/products` (browse + create), `/me` (identity), and `/orders` (reserve → pay → fulfil) are implemented and Cognito-authenticated; `/webhooks/stripe` is public and signature-authenticated.

The oversell-free guarantee rests on **guarded single-statement `UPDATE`s** — `ReserveStock`'s `quantity - num_reserved > 0`, and a status precondition on every order transition (`CompleteOrder`, `CancelPendingOrder`, `FailOrder`, `ExpireOrders`). Zero rows updated means "someone else got there first". This one idiom does triple duty: it prevents oversell, it makes at-least-once Stripe webhook delivery idempotent without a distributed lock, and it stops a double release from driving `num_reserved` negative. It is now covered by tests (`internal/orders/service_test.go`).

Tech stack: Go 1.26, chi v5 router, PostgreSQL via pgx/v5 + sqlc (hosted on [Neon](https://neon.tech)), goose migrations, Stripe (test mode) for payments, Redis (planned, not yet wired in), Amazon Cognito for auth, Docker + Terraform for deployment.

### Payment flow (the two halves)

`POST /orders` reserves stock (`pending`). `POST /orders/{id}/checkout` is the **synchronous** half: it creates a Stripe PaymentIntent and returns its `client_secret`, moving the order to `awaiting_payment`. It commits no stock. The **asynchronous** half is `POST /webhooks/stripe` → `stripe_events` table → in-process worker → `CompleteOrder` + `CommitStock`.

The Stripe API call deliberately sits *between* two short transactions rather than inside one — an outbound HTTP call holding a row lock on contended inventory would make Stripe's latency into every other buyer's lock latency.

Two independent background goroutines run in-process, started in `mount()` and cancelled by the shutdown context:

- **`payments.Worker`** drains `stripe_events` (`FOR UPDATE SKIP LOCKED`, one event per transaction).
- **`orders.Sweeper`** expires reservations past `orders.expires_at` and releases their stock. **Deliberately not coupled to the Stripe worker**: expiry is our rule on our clock, so stock comes back on sale even if the processor never calls back. It touches none of `ReserveStock`'s guard, keeping the contention strategy swappable after profiling.

**The paid-but-expired race is real and handled loudly, not silently.** If a payment succeeds for an order the sweeper already expired, `CompleteOrder` matches zero rows; the worker stamps the event processed with `last_error` set and logs at ERROR for manual refund. Retrying cannot fix it, so it must not spin.

## Commands

- `make server` — runs goose migrations (`goose up`) against Neon, then runs the API (`go run ./cmd`), both via `scripts/with-env.sh` (see below). This is the standard way to run the app locally. There is no local Postgres container — `.env` must point at a real (Neon) database.
- `make clean` — tears down: `scripts/with-env.sh goose down`.
- **Frontend** (`web/`, needs Node 22): `npm ci` once, then `npm run dev` (Vite on `:5173`), `npm run lint`, `npm run typecheck`, `npx vitest run`, `npm run build`. Running the two halves separately needs `CORS_ALLOWED_ORIGINS=http://localhost:5173` on the server and `VITE_API_BASE_URL=http://localhost:8080` in `web/.env` (copy `web/.env.example`). Alternatively `npm run build` once and let `make server` serve `web/dist` on `:8080` with no CORS at all — which is what production does.
- Build/vet/test directly with the Go toolchain, e.g. `go build ./...`, `go vet ./...`, `go test ./...` (see Testing below).
- Requires `goose` CLI installed locally and a `.env` (copy `.env.example`) with a live Postgres connection string plus `COGNITO_ISSUER_URL`/`COGNITO_CLIENT_ID`.
- `scripts/with-env.sh <cmd>` — reads `.env` line-by-line (`KEY=VALUE`, **no quoting** — see below) and execs `<cmd>` with those vars exported. Used instead of shell-`source`ing `.env` directly, because the Neon DSN contains a literal `&` (from `?sslmode=require&channel_binding=require`), which a shell interprets as "run in background" — `with-env.sh` reads each line via `read` instead of evaluating it, so DSN special characters are inert. This is also why `.env` values are unquoted: that format is what `docker run --env-file .env` expects too (Docker doesn't strip quotes the way a shell would), so one `.env` format now works for both consumers.
- `docker build -t doorbust:latest .` / `docker run --env-file .env -p 8080:8080 doorbust:latest` — build/run the container locally. `Dockerfile` is a multi-stage Alpine build; the final stage needs `ca-certificates` since the app makes outbound TLS calls to both Neon and Cognito's JWKS endpoint, and runs as unprivileged uid 10001 (`USER doorbust`), not root.
- **Deploying (normal path)**: push to `main`. `.github/workflows/ci-cd.yml` runs `build` + `test` + `web`, then `deploy` builds the image (frontend included), pushes it to ECR tagged with the git SHA, runs `goose up` against Neon, and drives the rollout on the box via SSM Run Command (`docker pull` → retag to `doorbust:latest` → `systemctl restart doorbust` → `curl localhost:8080/health`). See "CI/CD" below.
- **Deploying (manual/local path)**: `terraform -chdir=infra apply` provisions the infrastructure (a single EC2 instance — no ALB, no ECS — see `infra/` below), then `./scripts/deploy.sh` builds the image and ships it via `docker save | ssh | docker load`, bypassing ECR entirely. This is the escape hatch for when CI is broken or you want to test an uncommitted build; the pipeline is the normal path. Terraform itself is **always** applied by hand from a workstation — state is local, so CI cannot run it. `deploy.sh` builds with `--platform linux/amd64` explicitly — the EC2 AMI is x86_64, and `docker build` otherwise defaults to the host machine's architecture (an arm64 image silently `exec format error`s on the amd64 instance instead of failing at build time). CI does not need that flag: GitHub-hosted `ubuntu-latest` runners are already x86_64.
- **Testing a protected endpoint by hand**: `./scripts/with-env.sh ./scripts/get-test-token.sh <username> <password>` signs in as a Cognito user via `USER_PASSWORD_AUTH` and prints an ID token to `curl -H "Authorization: Bearer $TOKEN" ...` with. It takes the pool/client identifiers from `.env` (hence running it through `with-env.sh`) rather than hardcoding them. **No `COGNITO_CLIENT_SECRET` is needed** — the authoritative client is now public, and sending a `SECRET_HASH` to a client that has no secret is an error, so the script omits the parameter unless you set that variable (which is only for the older confidential client; never pass it as an argument, it would land in your shell history). `ALLOW_USER_PASSWORD_AUTH` must be enabled on the app client (`aws cognito-idp update-user-pool-client --explicit-auth-flows ...`, additive alongside whatever flows already exist) for this to work.

### Database / sqlc workflow

- Schema migrations live in `internal/adapters/postgresql/migrations/` (goose format: `-- +goose Up` / `-- +goose Down`).
- Hand-written queries live in `internal/adapters/postgresql/sqlc/queries.sql`.
- After editing a migration or `queries.sql`, regenerate the sqlc code with `sqlc generate` (config in `sqlc.yaml`). Never hand-edit the generated files (`db.go`, `models.go`, `querier.go`, `queries.sql.go`) — they're marked `DO NOT EDIT`.
- `GOOSE_DBSTRING`, `GOOSE_DRIVER`, `GOOSE_MIGRATION_DIR` (and the app's `DB_MAX_CONNS`/etc. pool knobs) live in `.env` (gitignored, not committed; see `.env.example` for the required keys). The Makefile loads `.env` via `scripts/with-env.sh` for both `goose` and `go run` — neither goose nor the app loads it on their own, and `cmd/main.go` panics via `env.MustGetString` if `GOOSE_DBSTRING` isn't set, rather than falling back to a hardcoded DSN.
- Prefer Neon's **direct** (non-`-pooler`) connection string over the PgBouncer-pooled one — the app already pools client-side via `pgxpool`, and pgx's prepared-statement caching doesn't play well with PgBouncer's transaction-mode pooling.

### CI/CD

`.github/workflows/ci-cd.yml` is the whole pipeline — three jobs in one file.

- **`build`**, **`test`** and **`web`** run on every push and pull request, in parallel. **`web`** does `npm ci` (not `install` — it fails on lockfile drift, the frontend's counterpart to the `sqlc diff` check), lint, `tsc --noEmit`, `vitest run`, and `vite build`. Building there matters for the deploy: the image build compiles the same bundle, so a type error fails the PR instead of the deploy. `build` does `go vet`, `go build`, and a `sqlc diff` drift check (the generated files are committed, so they can fall out of sync with `queries.sql`/the migrations). `test` starts a throwaway `postgres:17-alpine` **service container**, migrates it with `goose up`, and runs `go test -race ./...`. Env vars are set directly in the workflow, **not** through `scripts/with-env.sh` — that script hard-requires a `.env` file that does not exist on a runner.
- **`deploy`** has `needs: [build, test, web]` and only runs on a push to `main`. Branch protection on `main` requiring the `build`, `test` and `web` checks is what keeps untested code off `main` in the first place; `needs:` only protects the deploy.
- Pinned tool versions live in the workflow's top-level `env` (`SQLC_VERSION`, `GOOSE_VERSION`). `SQLC_VERSION` **must** match the version that generated the committed code (see the header comment in `sqlc/db.go`) or `sqlc diff` fails spuriously.

Why SSM rather than SSH, given `scripts/deploy.sh` already exists:

- The security group admits `var.allowed_cidr` only (one `/32`). GitHub-hosted runners get unpredictable IPs, so a runner can neither SSH in nor `curl` port 8080. SSM Run Command is **outbound-only** from the instance, so nothing has to be opened. The post-deploy `/health` smoke test therefore runs *on the box* (`curl localhost:8080/health`).
- Terraform state is local and gitignored, so `terraform output -raw public_ip` is unavailable to a runner. The workflow finds the box with `aws ec2 describe-instances --filters Name=tag:Name,Values=doorbust-benchmark` instead. The public IP is ephemeral (no EIP), so never hardcode it.
- `infra/deploy_key` is Terraform-generated and gitignored; SSM removes the need for a key in CI entirely.

Two details that are load-bearing:

- The SSM script pulls `<ecr-url>:<sha>` and **retags it to `doorbust:latest`** rather than changing `deploy/doorbust.service`. That unit file is inlined into `user_data` via `templatefile`, so editing it changes `user_data` and **forces instance replacement** on the next `terraform apply`.
- `aws ssm send-command` returns as soon as the command is *queued*. The workflow polls `get-command-invocation` and fails on any non-`Success` status — without that the job would go green on a deploy that crashed.

Migrations run **before** the restart, so for a few seconds the old binary is serving against the new schema. Keep migrations backward-compatible (expand-then-contract).

**Rollback**: re-run the SSM command by hand with an older SHA tag, or `git revert` and push. ECR tags are immutable and a lifecycle policy keeps the last 5 images, so there are always 5 rollback targets and storage stays under the 500 MB Free Tier cap.

**One-time GitHub setup** (repo Settings):

- An **environment** named `production` with its deployment branch policy set to `main` only, holding the single **environment secret** `NEON_DSN` (the Neon direct, non-`-pooler` DSN — deliberately duplicated from the SSM `SecureString` so the CI role needs no decrypt rights). Environment-scoped rather than repo-scoped for a specific reason: repository secrets are exposed to `pull_request` runs from same-repo branches, so a PR adding a step that references the secret could exfiltrate it. The branch policy refuses the job before it starts. The `deploy` job's `environment: production` is what binds it. Leave *required reviewers* off — it would add a manual approval gate, contradicting auto-deploy on merge.
- **Repository variables** `AWS_REGION`, `AWS_ROLE_ARN`, `ECR_REPOSITORY_URL` (the last two from the matching `terraform output`s), plus the frontend's build-time configuration: `VITE_COGNITO_DOMAIN`, `VITE_COGNITO_CLIENT_ID`, `VITE_COGNITO_REDIRECT_URI`, `VITE_STRIPE_PUBLISHABLE_KEY`. Variables rather than secrets on purpose — see the `VITE_*` note below. Not secrets: knowing the role ARN grants nothing, because the OIDC trust policy demands a `sub` of `repo:<owner/repo>:ref:refs/heads/main`, which only GitHub can mint and only on `main`.
- Branch protection on `main` requiring `build`, `test` and `web`. (These checks won't appear in GitHub's picker until the workflow has run once.)
- **Cognito is already provisioned** (the pool is not Terraform-managed). Domain `us-east-24r4djeews.auth.us-east-2.amazoncognito.com`; **two** app clients on pool `us-east-2_4r4djeEWS`:
  - `doorbust-web` (`vq2conlr…`) — **public, no secret**, code flow + PKCE, scopes `openid email`. This is the one the SPA uses and the one the API verifies against. A public client is mandatory: Cognito demands the client secret in the token exchange for a confidential client, and a browser cannot hold one.
  - `doorbust` (`b2s6uv1s…`) — the original confidential client. Kept but no longer authoritative. **`COGNITO_ISSUER_URL`/`COGNITO_CLIENT_ID` now point at `doorbust-web`**, because `auth.NewVerifier` accepts exactly one audience — a token minted for the other client is rejected. Changing which client is authoritative means changing `.env`, `infra/terraform.tfvars` (Terraform owns the SSM param — edit the tfvar and apply, never `put-parameter` by hand or the next apply reverts it), and the `VITE_COGNITO_CLIENT_ID` repository variable together.

**One branch, one environment.** There is deliberately no `production` branch — a GitHub environment is a deployment *target*, not a branch, and trunk-based development is the right model for one box and one developer. If a second environment ever appears, promote the *same* SHA-tagged image to it rather than branching; that is what `IMMUTABLE` tags and SHA-based tagging exist to enable.

## Architecture

The app follows a small ports/adapters style layering, one package per domain feature:

- `cmd/main.go` — process entrypoint. Builds `config`, opens a `*pgxpool.Pool` via `postgresql.NewPool`, constructs the `application` struct, and starts the server.
- `cmd/api.go` — defines `application` (holds `config` + the pool), `mount()` which builds the chi router, wires middleware, and connects each feature's handler/service, and `run()` which starts `http.Server`. This is the composition root — new features get wired into `mount()` here.
- `internal/adapters/postgresql/` — `pool.go` owns the connection adapter: `postgresql.Config` (DSN + pool sizing) and `NewPool`, which parses the DSN, applies the pool knobs, and pings once so a bad DSN fails at startup. Pool sizing is read from env in `main.go` (`DB_MAX_CONNS`, `DB_MIN_CONNS`, `DB_MIN_IDLE_CONNS`, `DB_MAX_CONN_LIFETIME`, `DB_MAX_CONN_IDLE_TIME`).
- `internal/adapters/postgresql/sqlc/` — sqlc-generated DB layer (`Queries` struct implementing a `Querier` interface) plus the source `queries.sql`. Feature services depend on the `Querier` interface, not the concrete `Queries` type, so they can be tested/mocked independently of Postgres. `tx.go` (hand-written) defines the `Beginner` interface used for transactions; `*pgxpool.Pool` satisfies both it and the generated `DBTX`.
- `internal/<feature>/` (e.g. `internal/products/`) — each feature package has:
  - `service.go` — business logic behind a `Service` interface, implemented by an unexported struct wrapping a `repo.Querier`.
  - `handler.go` — HTTP layer behind an unexported `handler` struct wrapping a `Service`; methods are chi-compatible `http.HandlerFunc`s.
  New features should follow this same handler → service → repo.Querier shape and be wired into `mount()` in `cmd/api.go`.
- `internal/env/` — thin env var helpers: `GetString`/`GetInt`/`GetDuration` (each with a fallback), and `MustGetString` (panics if unset — used for `GOOSE_DBSTRING`, `COGNITO_ISSUER_URL`, `COGNITO_CLIENT_ID`, none of which have a safe default).
- `internal/json/` — the shared HTTP JSON layer. `Write(w, status, data)`, `Decode(r, dst)` (1 MiB cap, rejects unknown fields), and `WriteError(w, status, code, message)` / `WriteInternalError(w)`. **Handlers must not call `http.Error`** — it writes `text/plain`, which would leave the API returning two content types depending on outcome. Every non-2xx body is `{"error":{"code":"...","message":"..."}}`; the `Code*` constants are the stable, machine-readable half of the contract and cannot be renamed without a frontend change.
- `internal/customers/` — `GET /me`. Bridges Cognito identity to app identity: a Hosted-UI signup creates a user in the **pool**, not a row in **`customers`**, and before this the row appeared only as a side effect of a first successful order. `LinkCustomer` is an upsert, so `/me` is idempotent and safe to call on every page load.
- `internal/payments/` — the Stripe adapter. `gateway.go` implements the `orders.PaymentGateway` interface (declared in `internal/orders`, so the order lifecycle does not depend on who moves the money); `handler.go` is the webhook, which verifies the signature over the **raw** body and does nothing but record the event; `worker.go` drains the inbox. PaymentIntent creation uses an idempotency key derived from the order id, so a retried checkout returns the same intent instead of attaching a second chargeable one.
- `internal/auth/` — Cognito ID token verification. doorbust is a **resource server**, not an OAuth2 client: a separate frontend owns the Cognito Hosted UI login/callback and hands doorbust a bearer ID token on each request. `NewVerifier` wraps `coreos/go-oidc`'s `oidc.Provider.Verifier` (discovers the issuer's JWKS at startup, so a bad issuer URL fails fast like `postgresql.NewPool` does). `Middleware` checks `Authorization: Bearer <token>` and puts the caller's `Claims{Subject, Email}` on the request context; `FromContext` reads it back in handlers. Wired via a chi route group in `cmd/api.go`'s `mount()` around `GET /me`, `POST /products`, `GET /orders`, `GET /orders/{id}`, `POST /orders`, `POST /orders/{id}/checkout`, `DELETE /orders/{id}` — `GET /products*`, `GET /health*`, `POST /webhooks/stripe` and the storefront catch-all `GET /*` stay public. (`cmd/api_test.go`'s `routeAccess` table is the authoritative list; it is checked against the real router.) `internal/orders` uses the caller's email from context (not a client-supplied field) both as the order's owner on `CreateOrder`, and as an ownership check on `GetOrder`/`Checkout` (403 `ErrForbidden` on mismatch, via the customer-joined `FindOrderByID` query). No role/group-based authorization yet — any authenticated Cognito user can hit any protected endpoint.
- `internal/web/` — serves the compiled storefront. `Handler(distDir)` serves files under `distDir`, falls back to `index.html` for extensionless paths (so `/checkout/4192` survives a hard reload), and returns the standard JSON 404 for a missing file *with* an extension — falling back there would answer a deleted `.js` with 200 and a body of HTML. Reads are confined by `os.Root`, so a crafted path cannot escape the bundle. Deliberately disk-based rather than `//go:embed`: embedding needs `web/dist` to exist at `go build` time, which would break `go build ./...`, `make server` and the `build` CI job for anyone who has not built the frontend. Files are read per request, so **`npm run build` against a running server is picked up without a restart** — `vite build` empties `dist` rather than replacing the directory, and the `os.Root` handle stays valid. The one case that does need a restart is the directory itself being deleted and recreated (`rm -rf dist`), which leaves the handle pointing at the old inode and turns every request into the JSON 404.
- `web/` — the buyer-facing storefront: Vite + React + TypeScript + Tailwind, built from the Claude Design handoff. Routes map one-to-one to that canvas: `/`, `/signin`, `/auth/callback`, `/sale/:id`, `/checkout/:orderId`, `/orders`, `/orders/:id`. `src/lib/` holds the pure logic worth pinning (`money`, `time`, `status`, `errors`, `api`); `src/auth/` holds the PKCE flow and the session. Creating a sale is out of scope — `POST /products` is vendor-only and has no screen, though `/me`'s `is_vendor` is surfaced so the nav hook exists. See "The frontend" under Notes.
- `infra/` — Terraform: one EC2 instance (Amazon Linux 2023) in the default VPC, a security group scoped to `var.allowed_cidr` (never `0.0.0.0/0`), a Terraform-generated SSH key (`infra/deploy_key`, gitignored), and an IAM instance role that can only read SSM params under `/doorbust/*`. `COGNITO_ISSUER_URL`/`COGNITO_CLIENT_ID` are managed here as plain SSM `String` params (not secret); the Neon DSN is **not** — put it in SSM yourself as a `SecureString` so it never enters `.tf` files or state (`aws ssm put-parameter --name /doorbust/GOOSE_DBSTRING --type SecureString --value '...'`). `user_data` (`infra/templates/user_data.sh.tpl`) installs Docker and writes a script + the `deploy/doorbust.service` systemd unit that renders `/etc/doorbust.env` from those SSM params before each container start. State is local and gitignored — acceptable for a solo box, revisit with a remote backend if this becomes shared/long-lived; it is also why the CI pipeline looks the box up by tag instead of reading `terraform output`. The CI/CD half lives in the same files: an `aws_ecr_repository` (`IMMUTABLE` tags, lifecycle policy keeping 5 images), an `aws_iam_openid_connect_provider` for GitHub plus the `doorbust-github-actions` role it can assume — its trust policy pins `token.actions.githubusercontent.com:sub` to `var.github_oidc_subject`, which is what stops any other repo on GitHub from assuming it. **That claim is not the obvious string**: a job referencing an `environment:` gets `:environment:<name>` rather than `:ref:refs/heads/<branch>`, and this repo (created after 2026-07-15) uses immutable subject claims embedding numeric owner/repo IDs. Read the real value from CloudTrail rather than assembling it by hand — see the variable's description for the command — and two additions to the instance role: `AmazonSSMManagedInstanceCore` (so the preinstalled SSM agent registers the box as a managed node; distinct from the `ssm:GetParameter` grant, which is about reading config) and ECR pull rights.

## Notes

- **Error responses**: handlers log the real error server-side (`log.Println(err)`) and return a static `"internal server error"` body on 500s. Never pass `err.Error()` into a 5xx response — pgx errors embed connection detail (e.g. ``failed to connect to `user=<db-user> database=<db-name>` ``) and would leak it to unauthenticated callers. Returning `err.Error()` for our *own* sentinel errors (`ErrOutOfStock`, `ErrOrderNotPending`, `ErrForbidden`) is fine and intended.
## Testing

`make test` (unit only, ~4s, no database) · `make test-db && make test-all` (everything) · `make cover` (adds the per-package floors) · `make test-db-stop`.

- **`internal/testsupport/` is the harness**, and it is a normal package, not `_test.go`, so `cmd` can import it — the router tests are the only way to exercise the real middleware chain. Nothing in production imports it.
- **Every database test gets its own database.** `testsupport.DB(t)` clones a migrated template per test and drops it after. That is what allows `t.Parallel()` and lets globally-scoped operations (the expiry sweep, the worker's queue claim) be asserted to an exact count. The template's name embeds a **hash of the migration files**: all packages share one, a migration change forces a rebuild, and the processes `go test ./...` starts cannot race. Creation is serialised with a Postgres advisory lock and promoted from a staging name only once fully migrated, so a crash cannot leave a half-built template. Needs `CREATEDB`.
- **Auth is tested against the real verifier.** `testsupport.NewIssuer` serves OIDC discovery and a JWKS and mints RS256 tokens; `oidc.ClientContext` points `auth.NewVerifier` at it with **no production change**. Expired, wrong-audience, wrong-issuer and forged tokens are all genuinely rejected rather than stubbed past.
- **Stripe is stubbed at the HTTP layer**, not behind `orders.PaymentGateway`, so tests assert what we actually send — amount, currency, `Idempotency-Key`, `metadata[order_id]`. A fake interface would accept a checkout that charged the wrong amount. `NewStripeGateway` takes variadic `stripe.ClientOption` for this; production passes none.
- **`TestEveryRouteIsClassified` is the highest-value test here.** It walks the real router with `chi.Walk` and fails if any route is missing from the `routeAccess` table in `cmd/api_test.go`. A new route with no entry fails by default — which is exactly how `POST /products` shipped ungated. When you add a route, add its access level; do not delete the case.
- **DB tests skip when `TEST_DATABASE_URL` is unset**, so `go test ./...` is green with no database. `make test` clears the variable explicitly so it stays fast even if you export it.
- **The frontend suite pins its own `VITE_*` env** in `vite.config.ts`'s `test.env`. `web/.env` is gitignored, so without that pin the suite reads whatever a developer happens to have set: adding `VITE_API_BASE_URL=http://localhost:8080` silently rewrote every URL the tests assert on, and the suite passed in CI while failing on the machine with the file. Tests must not depend on untracked local config.
- **The frontend has its own suite** (`cd web && npx vitest run`), scoped to the logic with real branching rather than to markup: money formatting refuses non-integer cents; the countdown derives from `expires_at` and floors rather than rounds; every one of the six order statuses and eight error codes has copy, and `forbidden` is asserted to render *identically* to `not_found`; the API client turns a non-JSON 5xx into an `ApiError` rather than a parse failure. The one component test is `Checkout.test.tsx`, which asserts `POST /checkout` fires exactly once under a StrictMode double-mount — the failure mode a state-based guard actually has.
- **Coverage floors are per package** (`scripts/check-coverage.sh`): orders/payments ≥85, auth/json ≥90, products/customers ≥80, web ≥85. No floor exists for the frontend — Vitest coverage is not wired in, and the Go floors are unaffected by `web/`. No floor on `cmd`, `env`, `adapters`, or generated sqlc — a global number is dominated by generated code and can be met while the oversell logic goes untested. Requires `-coverpkg=./...` or the `cmd` tests credit their coverage nowhere.
- CI runs `-race -shuffle=on`. Shuffle catches order dependence; per-test isolation is what makes passing it possible. Use `-count=N` locally — concurrency bugs are probabilistic and a single pass can succeed by luck.
- **Load testing is deliberately out of scope** and belongs on the EC2 box, not on 2–4 shared CI vCPUs.
- Graceful shutdown **is** implemented: `run()` uses `signal.NotifyContext` (SIGINT/SIGTERM) plus `errgroup`, draining `http.Server.Shutdown` and cancelling both background goroutines within `SHUTDOWN_TIMEOUT` (default 15s). SIGTERM is what both `systemctl restart doorbust` and `docker stop` send. Nothing is lost without it — every write is a guarded `UPDATE` and unprocessed events are re-claimed — but in-flight requests no longer vanish on deploy.
- **Stripe events are PULLED, not pushed.** Stripe cannot reach the box: the security group admits one `/32`, there is no Elastic IP, no domain, no ACM cert and no reverse proxy — the app is plain HTTP on `:8080`. Rather than buy all four, `payments.Poller` lists `/v1/events` on a timer and writes into the same `stripe_events` inbox the webhook writes to; the worker is identical either way. This needs **no infra change and no Stripe dashboard configuration**, and it catches up after a redeploy or outage by construction, which a push would not. The webhook endpoint is kept for local `stripe listen`; running both is safe because `InsertStripeEvent` dedups on Stripe's event id. `STRIPE_WEBHOOK_SECRET` is effectively local-only now.
- **The poller's overlap window is load-bearing, not padding.** Its cursor is `max(stripe_created_at)` — Stripe's clock, not ours, because `received_at` moves with our downtime. Since a timestamp is not a strict sequence, each poll rewinds by `STRIPE_EVENT_POLL_OVERLAP` (2m). Without that rewind an event created slightly out of order is skipped *permanently*. Re-scanning costs nothing (the insert dedups), so never "optimize" it away.
- **`HandledEventTypes` (`internal/payments/events.go`) is shared** by the poller's fetch filter and the worker's routing. `TestHandledEventTypesAreRouted` fails if they drift — a type fetched but unrouted is silently ignored; one routed but unfetched never arrives.
- `STRIPE_SECRET_KEY` needs **no Terraform change**: `render-doorbust-env.sh` pulls every `/doorbust/*` param `--with-decryption`, so adding it as an SSM `SecureString` by hand is enough (same precedent as `GOOSE_DBSTRING`).
- **`aws_instance.doorbust` pins its AMI via `lifecycle { ignore_changes = [ami] }`.** `data.aws_ami.al2023` uses `most_recent = true`, so its id moves whenever Amazon publishes a new AL2023 image — which previously meant *any* `terraform apply` after such a release would terminate and recreate the box. The replacement comes up with **no container image loaded** (the image is pushed by a deploy, not baked in) and gets a **new public IP**, so the app stays down until a redeploy. To move AMIs deliberately: `terraform apply -replace=aws_instance.doorbust`, then redeploy.
- **The frontend ships inside the API image and is served at the same origin.** This is forced, not chosen. The box has no Elastic IP, no domain, no TLS and a security group admitting one `/32` — the same facts that make Stripe events *pulled* rather than pushed — so a browser on the open internet cannot reach `:8080`. An S3/CloudFront bundle would load and then fail every API call. Serving from the Go binary needs no new AWS resource, and it keeps one deploy artifact and **one rollback target**: retagging an older SHA moves the API and the storefront back together. The Dockerfile's `node:22-alpine` stage builds `web/` and copies `dist` to `/srv/web`; `WEB_DIST_DIR` points the handler at it.
  - **`VITE_*` values are baked in at image build time**, not read from the container environment — Vite inlines them into the bundle. They are passed as `build-args` from GitHub **repository variables**, never secrets: build args are visible in `docker history`, and each value (Cognito domain, *public* app client id, Stripe *publishable* key) is one the browser holds anyway. Never add `STRIPE_SECRET_KEY` or the DSN there; `docker build` warns `SecretsUsedInArgOrEnv` on the publishable key purely because its name ends in `KEY`.
- **CORS is a development affordance, not a production one.** `CORS_ALLOWED_ORIGINS` is unset in production precisely because the frontend is same-origin there. It exists so `npm run dev` on `:5173` can call `:8080`. Empty means the middleware is not mounted at all — closed by default, the same failure direction as `COGNITO_VENDOR_GROUP`.
- **The storefront's catch-all is a classified route.** `GET /*` has an entry in `routeAccess` (public) and a probe in `TestRouteAccessIsEnforced`, like every other route. It is registered **last** and as `GET` only, so specific patterns still win and a POST to an unknown path is a 405 rather than a page.
- **Three frontend rules are load-bearing against real API behaviour**, and each is guarded in code rather than by convention: `POST /orders` is **not idempotent** (a retry reserves a second unit), so the reserve button guards on a `useRef`, not on state — two fast clicks both observe stale state; `POST /orders/{id}/checkout` is valid only on a `pending` order and flips it, so it fires from a ref-guarded mount effect (React StrictMode double-mounts every effect, which a state guard lets through — `web/src/routes/Checkout.test.tsx` asserts exactly this); and **a successful Stripe confirm is not a completed order** — the webhook worker completes it, so only `status === "completed"` from `GET /orders/:id` may render as paid. The reservation countdown derives from `expires_at`, never a literal 15:00, because `RESERVATION_TTL` is server config.
- **Hosted UI sign-in cannot work on the deployed box, and no amount of config fixes it.** Cognito refuses to register a callback URL that is not HTTPS, with a single exemption for `http://localhost`. The box is plain HTTP on an ephemeral IP with no domain and no TLS, so `http://<ip>:8080/auth/callback` is rejected outright at `create-user-pool-client` time — this is the same missing TLS that forces Stripe events to be pulled rather than pushed, surfacing a second time. Registered callbacks are therefore `http://localhost:5173/auth/callback` (Vite) and `http://localhost:8080/auth/callback` (the built bundle served by `make server`, which is the production topology minus TLS). **The deployed box can serve the storefront and its public browsing, but nobody can sign in on it.** Fixing that means a domain + certificate, which is a deliberate, separate decision — see Future work.
  - The exemption is the **loopback hosts**: `localhost` *and* `127.0.0.1` are both accepted over plain HTTP (verified against the real pool); every other host is rejected at `create-user-pool-client` time with "cannot use the HTTP protocol". `callbackOriginUsable` in `web/src/lib/config.ts` encodes exactly that rule, and `/signin` renders an explanation instead of a Continue button when it returns false. Without that check the box shipped a button whose only possible outcome was a bare Cognito error page reading `error=redirect_mismatch` — the config is *valid*, it just cannot include this origin.
- **The dev token-paste sign-in cannot reach production.** `/signin` gains a paste-an-ID-token form when `VITE_ENABLE_DEV_TOKEN_LOGIN=true`, for driving the app before the Cognito Hosted UI exists. It is guarded by `import.meta.env.PROD` as well as the flag, so the constant folds to `false` and the bundler drops the component — verified by grepping a production build made *with* the flag set.
- **Authorization is one Cognito group.** `POST /products` is wrapped in `auth.RequireGroup(vendors)`; everything else authenticated is open to any signed-in user. Membership rides in the ID token's `cognito:groups` claim, so **granting it only takes effect on the next token** — an open session keeps its old claims until refresh. `GET /me` returns `groups` and `is_vendor` so a client can decide what to render instead of probing for a 403. Terraform owns the group (`aws_cognito_user_group.vendors`) even though the pool itself is out-of-band; granting is `aws cognito-idp admin-add-user-to-group`.
- **`orders.status` strings are triple-coupled**: the `CHECK` constraint in migration `00006`, the constants in `internal/orders/status.go`, and the public API contract. Renaming one requires a migration and a frontend change.
- **`/health` is liveness; `/health/ready` is readiness.** `/health` returns a static `all good` and touches nothing — kept that way because the deploy's restart loop depends on it answering while the app is still settling. `/health/ready` pings the pool and reports the Stripe poller's last successful poll, returning **503** when the database is unreachable or the poller is stale/failing. That is what the post-deploy smoke check looks at, because it fails on exactly the conditions that leave the app running but useless: wrong DSN, revoked Stripe key, stalled poller.
  - The poller distinction that matters: **"has not succeeded yet" versus "has never succeeded"**. A poller failing every tick — an invalid key — must not report `starting` forever, or a deploy with dead payments passes. `pollerStatus` in `cmd/ready.go` is a pure function for exactly this reason; its elapsed-time cases are impractical to drive through a live poller.
- **The `deploy` job is the one part of the pipeline a pull request cannot exercise** — it is gated on `push` to `main`, so its first real execution is always against production. Every pipeline failure so far has been in `deploy`, none in `build`/`test`. The mitigation is step ordering, and it is deliberate: assume-role, image build/push, and `goose up` all happen *before* the container restart, so a failure in any of them leaves the running app untouched. Preserve that ordering when editing the job.
- **OIDC trust failures are diagnosable, not guessable.** `Not authorized to perform sts:AssumeRoleWithWebIdentity` deliberately says nothing about why. The actual `sub` claim presented is in CloudTrail under `userIdentity.userName` — read it from there rather than reasoning about what it ought to be (see `var.github_oidc_subject`).
- **CI installs `sqlc` and `goose` from upstream prebuilt binaries, not `go install`.** `go install` compiles them from source on every run — `sqlc` vendors a full PostgreSQL parser and a WASM runtime — and neither tool's dependencies are in this repo's `go.sum`, so `setup-go`'s cache does not help. The tradeoff is that a release download has no `GOSUMDB` equivalent, so each is pinned to a SHA-256 verified with `sha256sum -c`; the version and hash sit together in the workflow's top-level `env` and must be updated as a pair. `goose` publishes a `checksums.txt`; `sqlc` does not, so its hash was computed by hand. Note the `sqlc` asset name drops the leading `v` (`${SQLC_VERSION#v}`). Because of this, the `deploy` job needs no Go toolchain at all and has no `actions/setup-go`.
- **Pinned GitHub Actions need periodic bumping.** GitHub deprecates the Node runtime that JavaScript actions execute on (Node 20 leaves the runners 2026-09-16), and the warning appears on a repo with no JavaScript in it — it refers to the action's runtime, not the project's. When bumping, remember that `configure-aws-credentials`, `amazon-ecr-login`, `setup-buildx-action`, and `build-push-action` are used **only in `deploy`**, so a green PR does not validate them; check their release notes for input changes instead of relying on CI.

### Future work

Roughly in dependency order. (The oversell concurrency test and graceful shutdown, formerly items 1 and 5, are **done** — see Notes.)

0. **Flip `LinkCustomer`'s conflict target to `cognito_sub`.** Migration `00005` is the expand phase: the upsert still keys on `email` so no data migration was needed, and `owns()` in `internal/orders/service.go` falls back to email for rows predating the column. Once every row is backfilled, key on `sub` and drop the fallback — email is mutable in Cognito, `sub` is not.
1. **Auto-refund the paid-but-expired case.** Today the worker flags it with `last_error` and an ERROR log for manual reconciliation. Deliberately manual first: a bug in an automatic refund path issues refunds in a loop.
2. **Rollback on a failed post-deploy health check.** Today a failed check turns the job red but leaves the box running the broken image; recovery is manual. This is cheap to add because the pieces already exist: ECR tags are immutable git SHAs and the lifecycle policy keeps five, so "on failure, retag the previous SHA and restart" is a few lines in the SSM script. **Build this before broadening smoke tests** — more smoke coverage without rollback only detects breakage faster, it does not fix it.
3. **Smoke tests beyond `/health`**, in rising order of value and cost. They must run *on the box* via SSM, because the security group admits only `var.allowed_cidr` and a GitHub runner cannot reach `:8080`:
   - `GET /products` — exercises `pgxpool` and a real query; nearly free, and catches the whole "app is up but the DB layer is broken" class.
   - An authenticated read (e.g. `GET /orders/{id}`) — `scripts/get-test-token.sh` already does `USER_PASSWORD_AUTH`; a dedicated smoke user's credentials in the `production` environment would cover Cognito/JWKS misconfiguration.
   - The full reserve → checkout flow — highest signal, but it **consumes real inventory** in the production database. Needs a dedicated smoke SKU with large stock, or a cleanup step. Decide that before building it.
4. **Scheduled heavy concurrency runs** — `on: schedule` plus `workflow_dispatch`, reusing the same Postgres service container with much larger settings (`-count`, goroutine counts, stock/order matrices). Concurrency bugs are probabilistic, so a single fast PR run can pass by luck for weeks. Caveats: this is for **correctness, not performance** — GitHub-hosted runners are 2–4 shared vCPUs and `-race` adds serialization, so throughput numbers belong on the EC2 box, not here. Keep hammering the container rather than Neon. Also note GitHub disables scheduled workflows after 60 days of repo inactivity, `schedule` only runs on the default branch, and a nightly ~10-minute run is roughly 300 of the 2,000 free private-repo minutes per month.
5. **A domain and TLS, which is now the blocker for a usable deployment.** It was previously a convenience — it would let Stripe push webhooks instead of being polled. It is now a hard requirement for sign-in: Cognito will not register a non-HTTPS callback outside `localhost`, so the deployed storefront can browse but cannot authenticate. One decision buys both. The cheapest shape is a domain plus a reverse proxy terminating TLS on the box (Caddy or nginx with Let's Encrypt), which needs the security group opened to 443 and an Elastic IP so the A record stops moving; ACM + an ALB is the AWS-native alternative and costs more than the rest of this project combined. **Whichever is chosen, the callback URL and `VITE_COGNITO_REDIRECT_URI` must be updated together with it**, and an Elastic IP is worth taking regardless — the public IP changes on every instance replacement, which silently breaks any registered callback.
6. **Frontend follow-ups**, now that `web/` exists. In rough order of value: a **vendor screen** for `POST /products` (the only implemented endpoint with no UI — `/me` already returns `is_vendor`, so the nav hook is in place); **Vitest coverage thresholds** in the `web` CI job, to match the Go floors; and **e2e smoke coverage** of the reserve→pay flow, which is item 3's hardest case for the same reason — it consumes real inventory.
7. **Registration UX.** Cognito Hosted UI owns signup, so there is no `POST /auth/register` and no AWS SDK in the repo. `GET /me` bridges the two identity stores by upserting a `customers` row on first call. If the branded signup form ever matters more than that simplicity, adding the proxy means `aws-sdk-go-v2` plus `COGNITO_CLIENT_SECRET` (SECRET_HASH) handling.

Structural note: there is one environment, so every post-deploy test runs against production. The industry answer is a staging environment; for a solo benchmarking project that is overkill, and making failures self-correcting (item 2) is the cheaper substitute.
